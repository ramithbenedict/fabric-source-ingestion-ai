T.EN Digiteam · Synapse DPV1 → Microsoft Fabric DPV2

Migrating DPV1 to Fabric: simplify first, then move one project at a time

This hub plans the migration of code and architecture from Azure Synapse to Microsoft Fabric. It reads the DPV1 repository, splits every project into a source dataset and a data product, and shows where each object lands in Fabric. Data movement comes in a later phase.

1. What this is about

Three principles drive the migration.

Simplify

Remove hops before translating

CURATED, STG and the SPOT copy-back disappear. Six steps and six data copies become three, because OneLake lets the Warehouse read the Lakehouse in place.

Code first

The legacy code is the specification

Scripts read pipelines, SQL and notebooks to find every object and its lineage. People decide only what scripts cannot: naming, model choices, open points.

One at a time

One project per run, with a review gate

A developer migrates one source dataset or one data product, checks the plan, then builds. GAIA is the pilot.

In scope · this phase
  • Inventory, lineage and object mapping of every DPV1 project
  • Fabric workspaces, Lakehouses, Warehouses, database projects, pipelines, notebooks, connections, variable libraries
  • T-SQL stays T-SQL: dedicated-pool code moves through DACPAC to the Fabric Warehouse, with dialect fixes
  • Spark notebooks ported to Fabric; data flows, external tables and CETAS replaced
  • Equivalence tests, written but not run
Deferred · later phase
  • No historical or live data is copied from ADLS or the Synapse databases
  • History back-fill, parallel run and reconciliation
  • Consumer cut-over (Power BI, Dataiku, DataGalaxy)
  • Synapse decommissioning

5. How the migration runs

Two service offerings, four workflows, five agents. How each element is identified, how each service runs step by step, and how a source dataset hands over to its data products: see the Process tab.

1

Migrate the source dataset

Ingested directly from the source into LH_SDS_<SOURCE>: landing, raw (parquet), tables. No shortcut. It publishes a contract for the data products.

2

Expose it to the data product

LH_INP_SDS_<SOURCE> in the product workspace, with one OneLake shortcut per table the product reads, built from the contract.

3

Migrate the data product

Silver load procedures replace INP, LDW, CURATED and STG; DM becomes gold views; T-SQL stays T-SQL, through the DACPAC.

Process · from a name to ready-to-deploy, for each service offering

Two services, one chain: sources are migrated first, data products reuse what the source migration published

This tab explains how the migration works, step by step: how every DPV1 element is found, how a source dataset and a data product are migrated, and how the two are linked by lineage. The same logic runs in the repository scripts, so what you read here is what the agents do.

Rule · Source Dataset Migration

Only the source dataset, end to end

Identifies, maps and builds only the objects of the source and their lineage, in source-dataset/<SOURCE>/. Product steps reached from a source master are left to Data Product Migration; the products that read the source are listed for analysis only.

Rule · Data Product Migration

Sources first, then the product

Focuses on the product, its dependencies and its interactions with other products. It starts only when every source it is produced from is migrated. Otherwise the scripts stop before writing anything and name the missing sources; the developer confirms and migrates them first, in their own source-dataset folder.

10. Rules that never change

These rules apply to every project and every agent. The gap review checks most of them automatically.

T-SQL stays T-SQL

Procedures, views and tables are translated to Fabric Warehouse T-SQL, never to notebooks. Dedicated-pool code moves through the DACPAC.

No cleansed zone

Database → Files/raw (parquet, written once); API or files → Files/landing (as delivered) → Files/raw (parquet); then Lakehouse tables. Only the tables that copied are loaded; a failed table is listed with its error and the others still load. One loader notebook per source (plus a FLATTEN notebook for APIs and files), only where DPV1 had one. CLEANSED logic moves into RAW → tables.

No shortcut in a source dataset

Source datasets ingest directly from the source. Shortcuts exist only in data products, through LH_INP_SDS_<SOURCE>.

Each service stays in its lane

A source migration lists its consumers but builds nothing of them; a product migration reads contracts but never rebuilds a source.

Sources before products

A data product starts only when all its source datasets are migrated. The scripts stop and name the missing ones; they are migrated first, in their own folder.

No ADLS linked service, no dataset

DPV1 ADLS zones were Synapse storage: OneLake is built into the Lakehouse and reached by path. Fabric has no datasets.

Every parameter from VL_MAIN

DEV, UAT and PRD value sets. Pipelines read @pipeline().libraryVariables.X, notebooks vl.X; Lakehouse and warehouse connections too (workspace @pipeline().DataFactory), so every item deploys in one Git sync.

Nothing left behind

Every object of the export is in a scope, the shared framework or the platform, or listed with a reason in the estate register.

One project migration at a time

Framing and build scripts stop while another project has a stage in progress. Finish it or pause it; --parallel only when the owner agrees.

DPV1 is read-only

Scripts read the export; nothing is written back. Every output goes to the project folder.

13. Key learnings from the pilots

What the GAIA and GEOS runs taught, and how the framework handles it now.

CompletenessScopes alone missed 7% of the estate

About 240 objects (pipelines, notebooks, triggers, scripts) were in no scope. The estate register now accounts for every object of the export.

Call chainNotebooks call notebooks

NTBK_COMMON_CHILD_META_RAW_TO_CLEAN was run by another notebook, so GEOS missed it. notebook.run, %run and notebook names in parameters are now traced.

LineageConsumers are found from the data, not only the calls

No pipeline links GEOS to GSP_ANALYSIS, yet 8 GSP views read rpl_geos. Data tokens find it: 14 of 25 GEOS tables are used.
